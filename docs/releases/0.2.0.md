# LuxLedger 0.2.0

LuxLedger `0.2.0` is a coordinated breaking release. Upgrade all LuxLedger packages together:

| Package | Version |
| --- | --- |
| `@luxledger/core` | `0.2.0` |
| `@luxledger/http` | `0.2.0` |
| `@luxledger/postgres-adapter` | `0.2.0` |
| `@luxledger/fastify-routes` | `0.2.0` |
| `@luxledger/express-routes` | `0.2.0` |

## Trial-balance API migration

Trial-balance account rows no longer return `is_contra`. They now return `balance_side`, which reports the actual side of the calculated balance.

Before:

```json
{
  "account_id": "00000000-0000-4000-8000-000000000101",
  "code": "1000",
  "name": "Cash",
  "normal_balance": "DEBIT",
  "balance": "2500",
  "is_contra": false
}
```

After:

```json
{
  "account_id": "00000000-0000-4000-8000-000000000101",
  "code": "1000",
  "name": "Cash",
  "normal_balance": "DEBIT",
  "balance": "2500",
  "balance_side": "DEBIT"
}
```

Replace direct reads of `is_contra` with `balance_side`. If a consumer still needs the old derived flag, calculate it as:

```ts
const isContra = account.balance_side !== account.normal_balance;
```

Zero balances use the account's `normal_balance` as `balance_side`, so this expression remains `false` for a zero balance.

## Account-code migration

Create-account requests accept an optional, non-empty `code`. When omitted, it is stored as `null`. Account and trial-balance responses always include `code`, but its value may be `null`.

```ts
type AccountCode = string | null;
```

Codes are unique only when present and only within the same tenant ledger. Multiple accounts without a code are allowed.

## Database migration

Apply migration `0009_stormy_archangel.sql` before starting services built against `0.2.0`:

```sh
bun run db:migrate
```

The migration adds the nullable `accounts.code` column and a partial unique index for non-null codes. Back up the database and validate the migration in a test environment before production rollout.

## Upgrade checklist

1. Upgrade all five LuxLedger packages to `0.2.0`.
2. Replace `is_contra` reads with `balance_side`.
3. Update account response types so `code` is required and nullable.
4. Apply the database migration.
5. Run contract, type, unit, and PostgreSQL integration tests.
6. Deploy the migrated application and verify account creation and trial-balance responses.
