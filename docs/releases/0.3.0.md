# LuxLedger 0.3.0

LuxLedger `0.3.0` is a coordinated breaking release. Upgrade all LuxLedger packages and the copied OpenAPI contract together:

| Component | Compatible version |
| --- | --- |
| `@luxledger/core` | `0.3.0` |
| `@luxledger/http` | `0.3.0` |
| `@luxledger/postgres-adapter` | `0.3.0` |
| `@luxledger/fastify-routes` | `0.3.0` |
| `@luxledger/express-routes` | `0.3.0` |
| OpenAPI `info.version` | `0.3.0` |

Do not combine the `0.3.0` contract or adapters with the previous published entry contract. Entry polarity, persistence columns, idempotency payload comparison, and public request/response schemas changed together.

## Breaking entry contract

Transaction and hold entries now use one non-zero signed amount:

- positive `signed_amount_minor` means DEBIT;
- negative `signed_amount_minor` means CREDIT;
- every transaction or hold must sum to zero.

Before (`0.2.0`):

```json
{
  "account_id": "00000000-0000-4000-8000-000000000101",
  "direction": "DEBIT",
  "amount_minor": "1250",
  "currency": "USD"
}
```

After (`0.3.0`):

```json
{
  "account_id": "00000000-0000-4000-8000-000000000101",
  "signed_amount_minor": "1250",
  "currency": "USD"
}
```

The matching credit leg uses `"signed_amount_minor": "-1250"`. Zero, a leading plus sign, and negative zero are invalid. Transaction create, bulk create, correction, hold create, transaction/entry reads, and hold-entry reads all use the signed field.

Core callers must replace `{ direction, amountMinor }` entry inputs with `signedAmountMinor: bigint`. Persisted `EntryEntity.money.amountMinor` is signed; consumers that need a display label derive it from the sign and display the absolute magnitude.

Idempotent retries must send the exact migrated signed payload. Reusing an existing reference with a legacy-shaped or sign-changed payload is a payload mismatch, not an automatic conversion.

## Database migration semantics

Migration `0002_2026-10-06-signed-entry-amounts.sql` upgrades databases created from the consolidated `0000` baseline:

1. Rename `entries.amount_minor` and `hold_entries.amount_minor` to `signed_amount_minor`.
2. Negate existing CREDIT rows; existing DEBIT rows keep their positive value.
3. Convert posted balances, pending reservations, and balance snapshots to the unified signed convention.
4. Replace direction-based constraints, triggers, and grant-lineage checks with sign-based equivalents.
5. Reject zero signed entry and hold-entry amounts.
6. Drop the entry `direction` columns and the `entry_direction` enum.

The migration preserves accounting meaning: a legacy DEBIT 1250 becomes `1250`, and a legacy CREDIT 1250 becomes `-1250`. The PostgreSQL integration test in `packages/postgres-adapter/test/integration/signed-amount-migration.integration.test.ts` seeds legacy rows, applies `0002`, verifies the transformed values and constraints, and then rolls the fixture back.

## Upgrade procedure

1. Stop writers and take a database backup using the [backup/restore runbook](../runbooks/backup-restore-drill-mvp.md).
2. Upgrade the five LuxLedger packages as one set and replace every copied OpenAPI document with the `0.3.0` canonical file.
3. Update core inputs and HTTP clients to send signed amounts. Remove entry polarity branches based on a separate direction field.
4. In a disposable copy of production data, apply migrations and verify that all entry and hold-entry values are non-zero, each transaction and hold balances to zero, and CREDIT rows have become negative.
5. Run `bun run test:ci`, `bun run typecheck`, `bun run lint`, `bun run contract:verify`, and `bun run migration:verify` against the dedicated test database.
6. Apply migrations before starting `0.3.0` application code, deploy the coordinated package set, and smoke-test posting, idempotent retry, reversal/correction, holds, and entry reads.

## Rollback and restore

Migration `0002` is forward-only. Downgrading packages does not recreate the dropped columns or enum and must never be used as a database rollback.

If validation fails before the migrated service is exposed, stop the deployment and restore the pre-migration backup into a new database or schema. Point the complete `0.2.0` application set at that restored database. Do not partially reverse the SQL in place: reconstructing the legacy shape requires deriving direction from each sign, taking the absolute magnitude, restoring projection semantics, constraints, triggers, and the enum atomically.

After `0.3.0` accepts writes, a pre-migration restore discards those writes. Recovery therefore requires an operator-approved reconciliation or replay plan before traffic resumes. Keep the migrated database and backup until application and accounting checks complete.

## Compatibility matrix

| Application and contract | Database state | Result |
| --- | --- | --- |
| Published `0.2.x` entry contract | Before `0002` | Supported legacy state |
| Complete `0.3.0` set | `0002` applied | Supported signed-entry state |
| `0.3.0` application | Before `0002` | Unsupported; expected schema/column failures |
| `0.2.0` application | `0002` applied | Unsupported; legacy columns and enum no longer exist |
| Mixed `0.2.x`/`0.3.0` packages or OpenAPI | Any | Unsupported; contract and idempotency semantics can disagree |

Databases created from migration history older than the consolidated `0000` baseline are still not an in-place upgrade source; reset them as documented in the integration guide.
