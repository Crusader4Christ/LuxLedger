# LuxLedger 0.5.0

LuxLedger `0.5.0` is a coordinated breaking release. Upgrade all five packages together:

| Component | Release version |
| --- | --- |
| `@luxledger/core` | `0.5.0` |
| `@luxledger/http` | `0.5.0` |
| `@luxledger/postgres-adapter` | `0.5.0` |
| `@luxledger/fastify-routes` | `0.5.0` |
| `@luxledger/express-routes` | `0.5.0` |
| OpenAPI `info.version` | `0.5.0` |

## Breaking changes and upgrade

- `LedgerService.list`, `AssetService.list`, and `ReconciliationService.listRules` now
  accept `{ tenantId, limit, cursor?, where? }` and return `{ data, nextCursor }`.
  `ApiKeyService.listApiKeys` accepts the authenticated actor followed by
  `{ limit, cursor?, where? }`; tenant scope comes from the actor.
- HTTP ledger, API-key, and reconciliation matching-rule lists return
  `{ data, next_cursor }`. Ledger lists previously returned an array. Read `data`
  and follow `next_cursor` until it is null; `limit` defaults to 50 and is bounded
  to 1–200.
- `PaginationQuery` now takes a filter policy: replace
  `PaginationQuery<WhereFor<typeof policy>>` with `PaginationQuery<typeof policy>`.
  Replace `EntryPaginationQuery` with `PaginationQuery<typeof entryListFilter>`.
  Shared pagination helpers can accept `BasePaginationQuery`.

Upgrade all packages, regenerate the consumer lockfile and clients from the
`0.5.0` OpenAPI document, and update custom repository implementations to the
new paginated signatures. These changes complete the bounded list contract;
callers must migrate rather than rely on the former unbounded responses.

## Typed filters and reconciliation results

Core list queries derive `where` types from operation filter policies. HTTP list
endpoints accept URL-encoded JSON in `where`, using the documented snake_case
fields. Tenant scope and private fields cannot be overridden. Cursors bind to the
resource, tenant, fixed scope, and filters; keep the same filters for every page.
Timestamp cursors preserve PostgreSQL microseconds and immutable tie-breakers.

`GET /v1/reconciliation/runs/{id}/results` and
`ReconciliationService.listResults` provide paginated reconciliation results,
including status and nullable reference filters. Existing run responses and
reports remain unchanged. UUID path validation now accepts generated UUIDv7 IDs.

## Database and idempotency compatibility

No migrations changed relative to the published `0.4.0` baseline. Keep its complete
migration chain, including `0005_2026-10-17-add-credit-grant-list-index.sql`.
No data transformation or database reset is required. Posting, retry, and
idempotency semantics are unchanged.
