# Credit grant lots and allocation lineage (LL-84, LL-66)

See the [transaction write-path overview](./transaction-flows.md) for record creation, grant-specific branches and transaction boundaries.

## Reservation atomicity and recovery (LL-101)

Each partial commit is its own atomic transaction: a failed commit preserves the previous reservation and creates no posting or consumption lineage. A successful partial commit leaves the remainder reserved until a later commit or explicit void by the caller. Reversal compensates the committed posting; it never reopens the hold or replenishes its reservation. When that grant has expired, only unreserved restored capacity is expired in the reversal transaction; outstanding reservations remain commit-safe.

The latest `credit_grant_capacity_versions` row stores both `remaining_minor` and `reserved_minor`. Adapter reads fetch these together; database validation uses `active_credit_grant_reservation`, an indexed latest-version lookup rather than a history aggregate. Reserve appends a version with increased reserved capacity; hold-linked consumption decreases remaining and reserved together; void appends a version releasing only that hold's unconsumed allocations. Reversal leaves reserved unchanged. Triggers maintain these transitions in the same transaction, including direct SQL, and reject direct snapshot insertion/update/deletion. New versions record their source entry, allocation or voided hold. Existing financial versions are never rewritten. No fifth grant table is added.

Adapter writers acquire grant-enabled account locks in ID order before grant locks; ordinary account balance updates follow afterward. Commit and void additionally serialize on the hold row before taking account locks. The transaction-local allocation projection avoids repeatedly allocating the same capacity within one posting, not a second persistence authority. Commit/void still derive the unconsumed allocation of the specific hold/grant from its provenance; they do not replay every active hold for a grant. Tests independently replay provenance after each scenario and compare it to the latest reservation snapshot.

LL-101 uses one migration (0004), one reservation snapshot model and no transitional reads, writes or backfills. Migration DDL and lifecycle mutations are transactional. Integration tests verify failed-migration rollback; `bun run migration:verify` verifies clean installation and backup/restore.

Hold lifecycle is `HELD -> HELD` for partial commit, `HELD -> APPLIED` for full commit, and `HELD -> VOIDED` for release. Final states cannot be updated or reopened. Remaining amount is positive while HELD and zero in a final state. For grant-backed holds, a partial-commit update must match the committed posting total and proportional entries; direct SQL cannot change the remainder independently. Violations fail the transaction with internal SQLSTATE `LL001`, mapped to `HOLD_LIFECYCLE_MISMATCH`. Insufficient reserved capacity uses `LL002`, mapped to `INSUFFICIENT_RESERVED_CAPACITY`. Invalid allocation relationships use internal `LL003`, exposed only as generic `INVARIANT_VIOLATION`, without database diagnostics or tenant identifiers. An identical commit retry returns the original posting with the current hold state, including `VOIDED` if the remainder was subsequently released.

### Database access configuration

Database roles belong to the host application's deployment, not the library: migrations do not create a runtime role. Use a separate non-owner login without superuser, BYPASSRLS, or inherited owner privileges. Set the trusted tenant context within each transaction. Hold, hold-entry and grant provenance policies enforce both tenant visibility and `WITH CHECK` on writes; hidden holds and grants return the same not-found responses as nonexistent records.

Functions use `SECURITY INVOKER`. The host must grant schema usage, reads and the inserts required by its enabled operations, including allocation inserts and trigger-generated capacity versions. Deny UPDATE, DELETE and TRUNCATE on allocation, lineage, capacity-version and hold-entry tables; append-only triggers additionally protect their contents. Hold transitions and account/balance projections require UPDATE. PostgreSQL row locking requires UPDATE privilege on at least one column: a column-level `UPDATE (id)` grant on credit_grants and transactions suffices for their locks, while immutable-row triggers prohibit actual mutations. The commit query locks only the joined grant rows, not immutable allocation history. These are permission requirements, not a universal role provisioning script; validate the host's complete operation set under its actual role. The integration test creates and rolls back its own restricted role and checks reserve, partial commit, void, tenant isolation and forbidden provenance mutations.

Credit grants are optional, immutable lot metadata layered over one account and its asset. They are not an account type and do not define an economic asset. Purchased credit, promotional credit, reward points, and similar distinctions belong in tenant assets and separate accounts when they have different accounting or spending semantics.

Grant eligibility is an immutable `grant_enabled` capability selected when the account is created. It is not inferred from grant existence and is never adopted or changed later. A grant-enabled account must use a registered asset, have `CREDIT` side and `DISALLOW` overdraft policy. A tenant may have any number of grant-enabled accounts, including accounts using different assets. Ordinary accounts remain valid for normal ledger transactions and do not acquire grant semantics.

`POST /v1/credit-grants` accepts `ledger_id`, `account_id`, `funding_account_id`, `reference`, `amount_minor`, optional `external_reference`, and optional immutable `expires_at`. PostgreSQL `transaction_timestamp()` is the issuance authority: a supplied expiration must be strictly later. The grant asset is derived from `account.asset_id`; it is not duplicated in the request or grant table. Before posting, the grant repository explicitly checks that the distinct funding account belongs to the same tenant and ledger and uses the same asset and compatible currency. An expiring grant cannot use a grant-enabled funding account because its eventual funding credit is ordinary expiration funding, not allocation lineage. The funding account's natural side and unrelated in-flight holds remain governed by ordinary posting and overdraft rules rather than grant-specific restrictions.

Every grant posts a balanced issuance transaction: the funding account is debited and the grant-enabled account is credited. The grant stores only its account scope, idempotency and external references, and issuance transaction linkage. The issuance entry is the authoritative granted amount. The grant row never stores an authoritative remaining or reversed balance.

The `(tenant_id, reference)` key is unique across all ledgers and accounts of a tenant. An identical retry returns the existing grant after comparing its tenant, ledger, account, complete immutable payload, and the amount derived from the issuance entry. Reusing the reference in another ledger or account produces an explicit scope conflict; another changed payload fails with `CREDIT_GRANT_CONFLICT`. The advisory lock is keyed by this exact tenant/reference pair, not by the whole tenant. Grant-related mutations lock touched grant-enabled account rows in account-ID order before grant rows. Ordinary funding accounts are not pre-locked; their balance projection is updated atomically in account-ID order. Grant creation, transaction posting, and entry linkage commit atomically under tenant RLS.

Entry-to-grant links are append-only financial lineage. `ISSUANCE` and `REVERSAL` identify a grant's funding lifecycle; `CONSUMPTION` allocates a debit to one or more grants; `COMPENSATION` restores the exact allocations of a reversed consumption; `EXPIRATION` removes unconsumed capacity with a debit to the grant account and credit to its original funding account. Each grant has exactly one issuance link and at most one full grant reversal link. Every lineage append atomically creates an immutable cumulative capacity version. That version is a rebuildable query index over the authoritative ledger and lineage, never a mutable grant status or balance. Direct version inserts and all version updates or deletes are rejected; direct lineage inserts pass through the same validation, grant lock, and version-append triggers as repository writes. Composite foreign keys and database triggers enforce tenant, ledger, account, asset, entry sign, transaction relation, expiration eligibility, positive lineage amount, complete entry attribution, and nonnegative derived capacity. Original links and capacity versions are never updated or deleted.

`POST /v1/credit-grants/{id}/reversal` fully compensates a grant only while its derived capacity is untouched. Its request reference is a tenant-level idempotency key in the reversal namespace. Retrying the same reference for the same grant returns the existing reversal, while reusing it for another grant or submitting a different reference after reversal fails with `CREDIT_GRANT_CONFLICT`. The amount is not retry input: every reversal derives and posts the complete immutable issuance amount. Partial refunds and already-spent clawback policy remain LL-87.

`GET /v1/accounts/{id}/credit-balance` returns a bounded summary only (no lots) without taking an account row lock. Lots are read through `GET /v1/accounts/{id}/credit-lots`, and grants through `GET /v1/credit-grants` (filters `account_id`, `reference`, `external_reference` for exact tenant-scoped lookup). All collection reads use `limit` (1-200, default 50) and an opaque `cursor`, and return `{data, next_cursor}`. Reads are ordered by the exact creation timestamp then id (lineage: entry creation, entry id, grant id), so pages are stable under timestamp ties and inserts after the current cursor. Cursors are versioned and bound to the endpoint, tenant, and filters that created them; changing any of those values requires restarting from the first page. Invalid limits or cursors return 400.

Granted, reversed, consumed, compensated, expired, and remaining come from each grant's latest immutable capacity version and reconcile to the authoritative ledger-entry total without an `effective_at` cutoff: this is the current posted balance, not a historical as-of balance. The mutable `accounts.balance_minor` projection is not an authority for this read and cache drift does not make grant history unreadable. Capacity versions can be reconstructed from the append-only lineage if verification ever finds a mismatch.

Generic transaction and hold contracts remain unchanged. A debit posted to a grant-enabled account is allocated automatically in the same database transaction. Eligible grants are locked and consumed by `expires_at ASC NULLS LAST, created_at ASC, id ASC`; each lock is held through commit, so concurrent consumers cannot claim the same capacity. Allocation reads one latest capacity version per locked grant, subtracts active hold reservations, and maintains an in-memory projection across all debit entries in the posting. If the ordered grants cannot cover the complete debit, both the posting and its tentative lineage roll back. Grant-row contention is therefore scoped to consumers of the same grant account. Ordinary accounts do not query or lock grant rows; their balance rows are locked only by the atomic balance update, unless a transaction also touches grant-enabled accounts.

A debit hold on a grant-enabled account reserves exact eligible grant lots in the same FEFO order. `credit_grant_hold_allocations` is immutable provenance rather than a mutable balance: outstanding reserved capacity is derived from the original allocation, append-only consumption lineage, and current hold state. Partial commits consume only those reserved lots, including after their expiration boundary; void atomically releases the uncommitted remainder. Expiration posts only unreserved capacity and may remove a released expired remainder in a later run. Account rows are locked in ID order before grant rows for reserve, spend, commit, release, reversal, and expiration paths.

A transaction reversal appends `COMPENSATION` links by copying the original transaction's grant-by-grant `CONSUMPTION` amounts. If that restores an already-expired grant, a matching `EXPIRATION` posting is appended before the outer transaction commits. Correction performs that exact compensation and re-expiration first, then allocates the corrected debit from currently eligible grants. Replaying the same posting reference returns its existing immutable allocation; changing the payload for that reference is an explicit conflict.

Audit traversal is available in both directions: `GET /v1/credit-grants/{id}/allocations` lists (paginated) consuming and compensating entries for a grant, while `GET /v1/transactions/{id}/credit-allocations` lists the source grants for one consumption or compensation transaction. These queries join immutable links to ledger entries; they do not consult a mutable grant balance.

Spend eligibility is strict: `expires_at` must be null or greater than both the posting's `effective_at` and PostgreSQL `transaction_timestamp()`. Equality is expired, so a backdated posting submitted after expiration cannot resurrect capacity. Eligible lots are locked and allocated by `expires_at ASC NULLS LAST, created_at ASC, id ASC`; the per-account in-memory projection is retained across every debit entry in the posting.

Expiration preview and run accept explicit `as_of` and a limit from 1 through 100. Preview is read-only and may inspect future dates. Run selects due rows in FEFO order, acquires their grant locks in deterministic account order with `FOR UPDATE SKIP LOCKED`, restores FEFO result order, then reads the latest capacity versions after those locks are held and posts only the current positive amount. Its transaction reference includes the grant ID and cumulative expired amount, making identical retries inert while allowing capacity restored later to receive a distinct expiration posting. See the [expiration runbook](../runbooks/credit-grant-expiration.md).

A database boundary rejects incomplete or mismatched attribution, unallocated grant-account holds, allocation mutation, over-reservation, spending reserved capacity through an unrelated transaction, and expiration of reserved capacity. Ordinary accounts and their transaction payloads remain unaffected.

Allocation, consumption policy, provenance metadata, and transfer/refund rules are intentionally deferred until a concrete product flow requires them. LL-66 owns deterministic allocation and consumption lineage. LL-85 owns expiration fields, entries, and eligibility enforcement. LL-67 and LL-89 may introduce organization ownership and spending authority around accounts, but LL-84 deliberately adds no user, organization, membership, or permission model.
